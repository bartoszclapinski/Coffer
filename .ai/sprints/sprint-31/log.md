- `--:--` 31-C decision — **JSON format is a schema, not `"json"`.** Verified against the local Ollama 0.40.15: with `format: "json"` both `qwen2.5:3b` and `qwen3.5` answered the categorisation prompt (asks for `[0, 1, 3]`) with an object (`{ "0": 0, "1": 1, "2": 3 }` / `{"Groceries":0,…}`), which `HybridCategorizer` cannot read; with a JSON-schema `format` (or none) both returned the array. `CompleteJsonAsync<T>` therefore sends a schema generated from `T` (`JsonSchemaExporter`, strict number handling so numbers stay `number`/`integer`, every property required but nullable ones may be null, the root not nullable), cached per type, falling back to `"json"` only if the type cannot be described; the answer is still parsed leniently (`AiJson.ExtractJson`). A nullable-typed object schema (statement shape) was checked with `curl` on `qwen2.5:3b` and produced the full object. **Thinking:** JSON calls send `think: false`; verified that `qwen2.5:3b` (no thinking capability) accepts `think: false` (only `think: true` returns 400 "does not support thinking") and `qwen3.5` answers in `content` without thinking. Tool turns leave thinking at the model default (`qwen3.5` thinks ~85–125 tokens on a chat tool turn); thinking tokens count against `num_predict`, which stays `MaxTokens` as specified — if a thinking model exhausts it, the tool path's empty-answer guard turns it into a normal error. (Corrected in the review fixes below: text turns originally also kept the default and had no such guard.)
